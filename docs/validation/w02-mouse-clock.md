# W02：鼠标与原生采集时钟

日期：2026-10-13 · 状态：受控最小闭环真实运行通过 · Windows 独立实验

**构建通过，受控模拟输入、原生窗口帧的时间关联、125%缩放坐标和一次暂停时间映射通过。** 这不是原版完整鼠标能力或录制暂停验收，也不是产品架构决定。

## 问题与实验边界

用户已选择 Qt 6，当前实验沿用 Qt 6.8.3、C++20、MSVC 和 Windows SDK 10.0.26100.0。产品依据仍为固定 Mac 原版提交 `fa24059a9ba7e769152b3c1de047d96aca873e1c` 与[能力清单](../parity-checklist.md)，没有调整首版范围。

本轮验证 C17/C18/C21 的部分底层条件：Windows 原生 WGC 帧时间与鼠标 hook 时间能否落在共同时间轴上，窗口移动后屏幕坐标如何转换为素材坐标，暂停区间如何从活动时间扣除。E13 校准和 E45 自动运镜仍需后续产品级验证。

Qt 只负责实验窗口；WGC/D3D11 采集和像素读回用于测量，不确定产品后端。仅捕获自身窗口。本轮不编码视频、不采集声音，也不声称完成鼠标形状、编辑器校准或实际媒体分段暂停。

## 官方依据与测量方法

- [SystemRelativeTime](https://learn.microsoft.com/en-us/uwp/api/windows.graphics.capture.direct3d11captureframe.systemrelativetime?view=winrt-26100)为合成器渲染帧时的 QPC 时间。保留原始 100ns 值，不能用取帧回调时间替代。
- [QPC](https://learn.microsoft.com/en-us/windows/win32/sysinfo/acquiring-high-resolution-time-stamps)需要记录频率并转换单位；它不代表 UTC 墙钟。
- [MSLLHOOKSTRUCT](https://learn.microsoft.com/en-us/windows/win32/api/winuser/ns-winuser-msllhookstruct)同时提供屏幕坐标、消息时间与注入标志。实验分别保存 hook 回调 QPC 与消息时间，不能直接把消息毫秒拼接到帧 PTS。
- [SendInput](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendinput)用于自身前台窗口内的少量模拟输入。模拟输入明确标记；它不等同于硬件鼠标延迟或人工操作验收。

受控点击改变唯一颜色状态，在真实捕获纹理中寻找对应状态，比较该帧合成时间与 hook 时间；取帧时间作为另一指标。改变窗口位置后重复输入，比较 hook 物理坐标与 Qt 鼠标事件实际逻辑坐标的双轴比例。暂停期间仍采集原始数据，只检查时间映射，避免把丢弃数据包装成暂停录制已实现。

## 程序、环境与复现

源码：[main.cpp](../../probes/windows-sync/main.cpp)、[CMakeLists.txt](../../probes/windows-sync/CMakeLists.txt)、[运行脚本](../../probes/windows-sync/run.ps1)、[独立证据检查器](../../probes/windows-sync/verify.py)。Qt Widgets仅用于实验夹具。没有引入新产品依赖。

运行环境：Windows 11、Qt 6.8.3 MSVC x64、Windows SDK、C++20、Release、CMake/Ninja。具体硬件信息仅在本地保存。

在交互式Windows桌面运行：

```powershell
& '.\probes\windows-sync\run.ps1' `
  -QtRoot 'C:\Qt\6.8.3\msvc2022_64' `
  -VisualStudioRoot 'C:\Path\To\VisualStudio'
```

程序显示置顶的640×360逻辑窗口，捕获其自身HWND。约0.8/2.2/3.6秒发送三组模拟移动和点击；约1.8秒移动窗口；原始时间2.5–3.5秒定义为暂停区间。证据收齐且运行至少4秒后结束，否则通常6秒结束，另有10秒事件循环退出定时器；线程内系统调用不是可强制终止的硬实时截止。

模拟点击前检查实际光标命中自身窗口、前台线程mouse capture不属于其他窗口、鼠标左键未按住。首次允许通过自身窗口点击激活，之后必须保持前台；外部鼠标输入或失焦导致失败。只有自身注入标记的事件进入证据，不保存其他应用的鼠标轨迹。正常结束时有条件恢复原光标位置。部分输入发送失败的释放补偿路径有代码检查，未通过故障注入验证。

默认将完整原始帧、像素采样、事件和关联保存在新的 `probe-results/sync-*/result.json`。用 Python 标准库独立核验（Python仅为检查工具，不是产品运行依赖）：

```powershell
& 'python' `
  '.\probes\windows-sync\verify.py' `
  '<本次结果目录>\result.json' --expect positive
```

检查器重算暂停区间交集、单调时间、帧时间不晚于取帧时间（容差1ms）、每次点击的首个匹配像素状态和双轴Qt坐标。报告结论基于程序检查和独立检查器同时通过，单看二进制退出码不替代证据复核。

加 `-NoInput` 运行负向场景：程序预期退出1，即使采集正常也因缺少点击证据而失败。对该JSON运行 `verify.py ... --expect negative`，检查器预期退出0，表示预期失败行为符合约定。传入已有的 `-OutputDirectory` 预期退出2，保留已有结果。

## 失败记录与限制

1. 最初构建出现WinRT命名空间冲突和Windows LONG向JSON转换歧义，已修复。受限环境运行返回“指定的服务未安装”、零帧；真实桌面可采集，不将该现象写成确定根因或平台不支持。
2. 初始窗口未获得前台导致主动失败。测试夹具改为置顶，首次点击只在自身窗口激活，并检查mouse capture；没有取消后续失焦保护。
3. 中间版本检测到外部输入而中止，保留[公开验证摘要](public-results.md)。即使三次画面关联已经存在，该次仍记为失败。
4. UI线程直接调用SendInput时偶发约1秒停顿、缺少首击DOWN，[公开验证摘要](public-results.md)仅匹配两次。将输入调用放到临时线程并保持Qt/hook消息循环响应后，两次完整闭环通过。这支持“阻塞同线程输入/事件循环影响夹具”的解释，但不是操作系统内部根因证明。临时线程和嵌套事件循环仅用于探针，不是产品线程架构。

历史失败JSON来自中间源码，不能假称与最终源码哈希对应。本报告保留它们用于诊断，最终可复现验证以清单中的源码和正负向记录为准。

本轮没有实际手动鼠标/高频轨迹压力测试、形状变化、事件hook权限失败回退、跨屏或改变DPI、两次真实媒体暂停/继续、暂停期间鼠标输入、标记/音频同步、剪切变速后的指针校准和自动运镜验收。单次暂停数学映射不能替代C21要求的完整视频/声音/鼠标/标记分段测试。W01的指定30FPS输出不一致仍未解决；本轮没有编码视频，也没有证明恒定30/60FPS。
